# 原理说明

本文记录本项目在实战中逆向、验证过的技术细节，便于他人扩展机型或排查问题。

## 一、OTA 查询接口

```
POST https://ota.lenovo.com/ota-server/firmware/query/for-text-desc
Content-Type: application/x-www-form-urlencoded

action=querynewfirmware
devicemodel=<机型代号>        # 如 TB323FU_CN / TB322FC_CN / TB321FU_CN
deviceid=<序列号 SN>
curfirmwarever=<当前精确版本串>
locale=zh
nationcode=CN
pid=                          # 可为空
ChecksumType=sha256
```

返回 XML（节选）：

```xml
<firmwareupdate>
  <num>1</num>
  <name>TB323FU_CN_..._2.0.12.199_ST_260812_to_TB323FU_CN_..._2.0.12.211_ST_260822</name>
  <object_to_name>TB323FU_CN_..._2.0.12.211_ST_260822</object_to_name>
  <md5>434cf9b3...</md5>
  <size>183430067</size>
  <downloadurl><![CDATA[https://otanew-cdn.lenovo.com/firmware/2026822154854529-6891.zip]]></downloadurl>
</firmwareupdate>
```

要点：

- **逐级下发**：查询版本 N 返回 `N → N+1` 的增量包，不是最新版。沿链循环查询即可还原整条升级路径。
- 无更新时返回空的 `<firmwareupdate/>`。
- CDN 两种域名：`otanew-cdn.lenovo.com`（增量）、`ota-cdn.lenovo.com`（部分跨版本/全量级包）。
- 其它已知端点（本工具未使用）：
  - `POST https://ota.lenovo.com/ota-server/firmware/config/query`
  - `POST https://ota.lenovo.com/engine/config?`
  - `POST https://ota.lenovo.com/engine/upgrade?`

### SN 白名单

内测（beta / `_DF_` 标记）链路只对该机型**内测白名单中的 SN** 下发；普通 SN 查询返回空。
实测：同一 SN 在 A 机型有效、在 B 机型无效 —— 白名单按机型区分。

## 二、payload.bin 结构

```
偏移 0..31     头部
   0..3        magic "CrAU"
   4..11       version (uint64 BE, =2)
   12..19      manifest_size (uint64 BE)
   20..23      metadata_signature_size (uint32 BE)
   24..27      metadata_size (uint32 BE)
偏移 32..      manifest（protobuf，长度 = manifest_size）
偏移 32+ms..   数据段（各操作以 data_offset 相对此起点定位）
```

> 注意：本设备族 payload 的 manifest 起始偏移为 **32**（已实测），
> 不同实现的头部字段顺序可能略有差异，遇到解析失败建议先按本结构试探。

### protobuf 字段（实测）

`DeltaArchiveManifest`：

| 字段 | 类型 | 含义 |
|---|---|---|
| 13 | repeated LEN | partitions（PartitionUpdate）|

`PartitionUpdate`：

| 字段 | 类型 | 含义 |
|---|---|---|
| 1 | LEN | partition_name |
| 6 | LEN | old_partition_info（f1=size varint, f2=hash 32B）|
| 7 | LEN | new_partition_info（同上）|
| 8 | repeated LEN | **install_operations** |

`InstallOperation`（联想版字段号）：

| 字段 | 类型 | 含义 |
|---|---|---|
| 1 | varint | type |
| 2 | varint | data_offset（相对数据段起点）|
| 3 | varint | data_length |
| 4 | repeated LEN | src_extents（Extent: f1=start_block, f2=num_blocks）|
| 6 | repeated LEN | dst_extents |
| 8 / 9 | LEN(32) | 哈希（src / dst）|

`Extent`：`{ block_size = 4096 }`，`start_block × 4096 = 字节偏移`

### 操作类型（InstallOperation 枚举）

| 值 | 名称 | 语义 | 数据在包里 |
|---|---|---|---|
| 0 | REPLACE | 原始数据 → dst | ✅ |
| 1 | REPLACE_BZ | bzip2 数据 → dst | ✅ |
| 4 | SOURCE_COPY | src → dst | ❌ |
| 6 | ZERO | 写零 | — |
| 8 | REPLACE_XZ | xz 数据 → dst | ✅ |
| 9 | PUFFDIFF | 基于 src 的 puffin 差分补丁 | ❌（补丁在包里，源必须提供）|
| 10 | BROTLI_BSDIFF | brotli 压缩的 bsdiff 补丁 | ❌（同上）|

> 实测：`payload-dumper-go` 支持除 **PUFFDIFF(9)** 外的全部类型；
> 含 PUFFDIFF 的分区（通常 `system` / `vendor` / `system_ext`）无法直接提取。

### 应用语义（关键）

增量包应用时，**目标分区初始化为"源分区的副本"**，再按顺序应用各 operation：

```
new_partition = copy(old_partition)
for op in install_operations:
    apply(op, new_partition, data_section)
```

不满足此语义（例如把目标分区初始化为全 0）会导致含 `SOURCE_COPY` 的分区哈希不符。

## 三、为什么提取分区必须提供"源镜像"

因为补丁是**相对上一版本内容**计算的：

```
原厂旧版本字节 ──补丁──▶ 正确的目标版本字节 ✅
被改过的字节   ──补丁──▶ 损坏数据 💥
```

update_engine 在应用时会校验源分区的哈希，正是为了阻止第二种情况。
所以从增量包提取目标版本分区时，必须提供 `pre-build` 版本的该分区镜像。

**自动走链提取**就是自动完成这条链路：

```
base(V0) ──delta V0→V1──▶ V1 ──delta V1→V2──▶ V2 ── ... ──▶ Vn
```

每一跳的产出自动成为下一跳的源。全量包（full payload）自带完整数据，无需源。

## 四、其它相关细节

### 版本串格式

```
五代 TB323FU：TB323FU_CN_OPEN_USER_Q00020.0_A16_ZUXOS_2.0.12.<num>_ST_<YYMMDD>
四代 TB322FC：TB322FC_CN_OPEN_USER_Q00041.1_V_ZUXOS_<x>.<x>.<num>_ST_<YYMMDD>
三代 TB321FU：TB321FU_CN_OPEN_USER_Q00002.0_W_DF_17.5.10.<num>_ST_<YYMMDD>
```

- `_DF_` = 内测（developer）构建
- 后缀日期为构建日期，**查询时必须精确匹配**

### 从包内读取版本串

```
payload_properties.txt        → FILE_HASH / FILE_SIZE / METADATA_HASH / METADATA_SIZE
META-INF/com/android/metadata → pre-build-incremental / post-build-incremental
```

`pre-build` 即"源版本"，`post-build` 即"目标版本"。

### 动态分区（super）

`system` / `vendor` / `product` / `odm` / `system_ext` / `*_dlkm` 是 **super 分区内的逻辑分区**，
不是独立 GPT 分区。相关处理（本仓库脚本可辅助）：

- QFIL 线刷包的 super 常被切成 `super_1..N.img` 分片（**原始分片，非 sparse**），
  需按 `rawprogram*.xml` 的 `start_sector` 偏移拼装 → `scripts/assemble_super_from_qfil.py`
- GPT 中 super 分区的真实大小解析 → `scripts/parse_gpt.py`
- LP 镜像的拆包/重打包建议使用 [avbroot](https://github.com/chenxiaolong/avbroot)
  （`avbroot lp info / unpack / pack`）

### A/B 槽位

设备为 A/B 双槽，分区名带 `_a` / `_b` 后缀；
当前槽位：`adb shell getprop ro.boot.slot_suffix`
